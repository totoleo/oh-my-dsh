# Publishing & Collaboration

This repository is a pnpm workspace: every directory under `plugins/` is an independent npm package. This document is for all collaborators. The default branch is `master`; repository: https://github.com/totoleo/oh-my-dsh.

> 中文: [PUBLISH.md](PUBLISH.md)

## Roles & permissions

| Role | Can do | Access |
| --- | --- | --- |
| Contributor | fork, branch, PR, issue, add changesets | none |
| Maintainer | review, merge, approve releases | GitHub write |
| Release manager | merge the Version Packages PR | npm publish rights for `@totoleo` |

- **Merge requirements**: CI green + at least one maintainer review; `master` is branch-protected.
- **Automated releases** use the `NPM_TOKEN` repository secret (npm Automation token, scope `@totoleo`, read-write). `GITHUB_TOKEN` is provided by Actions.

## Requirements

| Tool | Version | Purpose |
| --- | --- | --- |
| Node.js | >= 20 | CI and tests (local dev uses 26) |
| pnpm | 11.28.5 (the `packageManager` field) | workspace |
| npm | 11 | publishing |
| DSH | 0.2.1-rc.3 (verified 2026-10); minimum 0.2.1-rc.2 | install verification |

The plugin depends on DSH's goal service, `ctx.tools.guard`, and the `ask_user_question` answer attestation; below 0.2.1-rc.2, automatic exploration is not guaranteed. The requirement is documented rather than enforced with `engines.dsh` (semver prerelease ranges tend to reject later release candidates); add the field if machine enforcement is needed.

## Versioning & changelogs: changesets

- Every PR that affects a published package **must include a changeset**:

  ```bash
  pnpm changeset
  ```

  Pick the affected package(s) and the bump type, write a short user-facing summary, and commit the generated `.changeset/*.md` with the PR.

- Follow semver:

  | Change | Bump |
  | --- | --- |
  | Bug fix, copy, icon | patch |
  | New capability, backwards compatible | minor |
  | Incompatible tool schema / state / commands | major |

- `CHANGELOG.md` is generated by `changeset version`; do not edit it by hand.

## Contributor flow

1. Fork the repo and branch from `master`: `feat/<topic>` or `fix/<topic>`.
2. Change code; behaviour changes must update the tests under `plugins/<name>/test/`.
3. Verify locally:

   ```bash
   pnpm install
   pnpm -r test
   ```

4. Add a changeset: `pnpm changeset`.
5. Open a PR describing the motivation, scope and how it was tested; mark **BREAKING** changes explicitly.
6. Merge after CI is green and a maintainer approves.

### Verifying a PR without publish rights

```bash
cd plugins/wish-mode
npm pack --pack-destination ../../dist
```

Then point `plugin_manager install_bundle` at the generated `.tgz` (or at the package directory).

## Automated release flow

1. A PR with a changeset merges into `master`.
2. `.github/workflows/release.yml` runs `changesets/action`:
   - If there are unreleased changesets, it opens a **Version Packages** PR (bumps versions and generates changelogs).
   - Once that PR merges, `changeset publish` publishes to npm and creates the tag.
3. `.github/workflows/ci.yml` runs `pnpm install --frozen-lockfile --ignore-scripts` + `pnpm -r test` on every PR and push.

## Security settings (GitHub side)

These live in GitHub settings rather than the workflow files, but they define the release security boundary:

- **Branch protection (`master`)**: require CI and at least one review; block force pushes and direct pushes.
- **Environment `npm-release`**: add required reviewers so publishing needs human approval; `NPM_TOKEN` is only available inside that environment.
- **`NPM_TOKEN`**: an npm Automation token scoped to `@totoleo` read-write; rotate it periodically; never print it in a workflow.
- **PR safety**: CI runs on `pull_request`, so fork PRs get a read-only token and no secrets; do not switch to `pull_request_target`.
- **Dependency updates**: `.github/dependabot.yml` checks npm and GitHub Actions weekly.
- **Provenance**: the release workflow sets `npm_config_provenance=true`, so npm publishes with provenance (requires a public repo and `id-token: write`).
- **Action versions**: currently pinned to major tags; pin to commit SHAs where stronger assurance is required.
- **Caveat**: the Version Packages PR is created with `GITHUB_TOKEN`, so it does not trigger CI; review it manually before merging (or use a PAT, weighing the broader permissions).

## Manual publishing (first release / hotfix)

```bash
cd plugins/wish-mode
npm test
npm pack --dry-run

npm login --registry=https://registry.npmjs.org
npm publish --registry=https://registry.npmjs.org
```

Scoped packages need public access on first publish; `publishConfig.access` is already set to `public`.

## Post-release verification

```bash
npm view @totoleo/dsh-wish-mode version --registry=https://registry.npmjs.org
```

Install the exact version in DSH:

```text
plugin_manager install_bundle
target: "@totoleo/dsh-wish-mode@<version>"
```

Check: the "许愿" chip appears at the left of the composer and `wish_requirement` is in the tool list.
If the chip is missing, **restart DSH** (the client module graph is cached per process).

## Rollback & troubleshooting

| Situation | Action |
| --- | --- |
| Wrong version published | `npm deprecate @totoleo/dsh-wish-mode@<version> "reason"`; do not unpublish |
| Undo a local install | `plugin_manager remove_bundle` |
| `E403` / permission errors | Check npm login, scope access and 2FA |
| Published to the wrong registry | Pass `--registry=https://registry.npmjs.org` |
| Chip missing after install | Restart DSH (client module cache); a page refresh is not enough |
| Unwanted files in the tarball | Check the `files` field in `package.json` |
